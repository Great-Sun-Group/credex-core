Current System Analysis

The current system has the following API modules:

  • Member - User management and authentication
  • Account - Exchange account operations
  • AccountInternal - Internal account operations
  • AssetMarker - Digital asset management
  • Credex - Credit exchange transactions
  • Admin - Administrative functions
  • DevAdmin - Development and testing utilities
  • Notifications - User notification system
  • Recurring - Scheduled operations

Each module follows a consistent structure:

  • Routes define API endpoints and validation
  • Controllers handle request processing
  • Validation schemas ensure data integrity

8. Create Invoice Data Model
  • Define Invoice node structure ✅

Revised Invoice node structure (as reusable template):

(:Invoice {
  invoiceID: string,                 // Unique Invoice ID
  Lines: string,      // JSON array of line items (template) <-this needs to be InternalAccount name and amount for each. these represent/are the transactions debiting the seller's payment account and crediting other accounts as above,
  Amount: number,             // Template amount <- total amount. this represents/is the transaction (credex) debiting (decreasing) the seller's account and crediting the buyer's
  Denomination: string,           // Currency denomination
  Notes: string,              // Additional notes
  createdAt: datetime         // Creation timestamp
})

We'll add an optional invoiceID field to the /createCredex route, and add the GLid field onto the Credex node: 

(:Credex {
  GLid: string }) -[:EXECUTES]-> (:Invoice)

the createCredex route is where the instantiation of the template occurs, becoming both payment and reconciling GL entries for the seller, and (for now) just the payment entry for the purchaser.

Key relationships:

  • (:Invoice)-[:CREDITS_TO]->(:Account|AccountInternal)
  • (:Invoice)<-[:EXECUTES]-(:Credex)
  • (:Member)-[:SIGNED]->(:Signature)-[:SIGNED]->(:Invoice)
  • (:AssetMarker {GLid: "shared-id"}) - AssetMarkers share GLid with the Credex that executes the invoice

Phase 6: DCO Updates for AssetMarker Support ✅

10. Update DCO Process for AssetMarker Nodes
  • Modify DCO balance update logic to include AssetMarker nodes ✅
  • Add support for updating GeneralLedgerAmount, CXXmultiplier, and Denomination properties ✅
  • Ensure exchange rate calculations are applied consistently ✅

Implemented approach for DCO updates:

  • Use direct node type queries to update all AssetMarker nodes
  • Apply the same exchange rate logic used for Credex nodes
  • Update both CXX-denominated and currency-denominated AssetMarkers

Implementation for updating AssetMarker nodes:

// Update CXX-denominated AssetMarkers
MATCH (assetMarker:AssetMarker)
WHERE assetMarker.Denomination = "CXX"
SET assetMarker.GeneralLedgerAmount = assetMarker.GeneralLedgerAmount / newDaynode.CXXprior_CXXcurrent
WITH newDaynode

// Update currency-denominated AssetMarkers
MATCH (assetMarker:AssetMarker)
WHERE assetMarker.Denomination <> "CXX"
SET
  assetMarker.GeneralLedgerAmount = (assetMarker.GeneralLedgerAmount / assetMarker.CXXmultiplier) * newDaynode[assetMarker.Denomination],
  assetMarker.CXXmultiplier = newDaynode[assetMarker.Denomination]

# Purpose: Stores any data, including profile/account pictures
# Security: Encrypted at rest, no public access
resource "aws_s3_bucket" "asset_marker_data" {
  bucket = "credexbuckets2-assetmarker-data-${var.environment}"

  tags = merge(var.common_tags, {
    Name = "asset-marker-data-${var.environment}"
    Purpose = "AssetMarker Data Storage"
    DataClassification = "Application Data"
  })
}

# Enable versioning to maintain file history and prevent accidental deletions
resource "aws_s3_bucket_versioning" "asset_marker_data" {
  bucket = aws_s3_bucket.asset_marker_data.id
  versioning_configuration {
    status = "Enabled"
  }
}

# Enable server-side encryption for data at rest
resource "aws_s3_bucket_server_side_encryption_configuration" "asset_marker_data" {
  bucket = aws_s3_bucket.asset_marker_data.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

Database Relationships

The implementation will use these key relationships:

// Member to Account relationships
(:Member {vendor: true|false})-[:OWNS]->(:Account)

// Member to AssetMarker relationships
(:Member)-[:PROFILE_PIC_ORIGINAL_JPG]->(:AssetMarker)
(:Member)-[:PROFILE_PIC_200_JPG]->(:AssetMarker)
(:Member)-[:PROFILE_PIC_600_JPG]->(:AssetMarker)

// Account to AssetMarker relationships
(:Account)-[:ACCOUNT_PIC_ORIGINAL_JPG]->(:AssetMarker)
(:Account)-[:ACCOUNT_PIC_200_JPG]->(:AssetMarker)
(:Account)-[:ACCOUNT_PIC_600_JPG]->(:AssetMarker)

// AssetMarker relationships (simplified with GLid)
(:Account|AccountInternal)-[:CR {amount: number}]->(:AssetMarker {
  GLid: string,               // Shared General Ledger ID
  GeneralLedgerAmount: number,
  CXXmultiplier: number,
  Denomination: string
})-[:DR {amount: number}]->(:Account|AccountInternal)

// AssetMarker to AssetMarker relationships
(:AssetMarker)-[:USED_IN]->(:AssetMarker)

// Invoice as reusable template
(:Invoice {
  templateItems: string,      // JSON array of line items
  amount: number,             // Template amount
  currency: string            // Currency denomination
})-[:CREDITS_TO]->(:Account|AccountInternal)

// Credex executes Invoice
(:Invoice)<-[:EXECUTES]-(:Credex {
  GLid: string,               // Same GLid as related AssetMarkers
  InitialAmount: number
})

// Digital signature relationships
(:Member)-[:SIGNED]->(:Signature)-[:SIGNED]->(:Invoice|:Credex)

For more details on the data model, see the Data Model page.

Revised Technical Considerations

  • GLid for Related Entities: Use a shared GLid field to group related AssetMarkers and Credexes, enabling balance verification and aggregation without complex relationship structures.
  • Single CR/DR Relationships: Maintain simpler single CR/DR relationships for AssetMarkers, with the GLid providing the grouping mechanism for related entries.
  • Reusable Invoice Templates: Design invoices as reusable templates that can be executed multiple times, with each execution creating a new set of AssetMarkers and a Credex sharing the same GLid.
  • AssetMarker Properties: AssetMarker nodes must include GeneralLedgerAmount, CXXmultiplier, Denomination, and GLid properties to support proper accounting and exchange rate handling.
  • DCO Integration: Use direct node type queries to update all AssetMarker nodes during the DCO process, applying the same exchange rate logic used for Credex nodes.
  • Digital Signatures: Invoices must be digitally signed by the creating member using the digitallySign utility.
  • Relationship Naming: Use ACCOUNT_PIC_* for relationships between accounts and asset markers (these may be displayed as product images on the client side).
  • Error Handling: Implement comprehensive error handling and validation to ensure data integrity.
  • Performance: Consider the performance implications of complex queries, especially those involving multiple relationships.
