Local CI/CD Pipeline Deployment Guide

This guide covers the local deployment system that replaced previous AWS-based infrastructure.

Overview

The local CI/CD pipeline automatically deploys services to the local production environment using GitHub Actions workflows that call deployment APIs running on the local server.

Server Restart Procedure

This comprehensive procedure covers all steps needed to restart and verify the complete deployment system after a server shutdown or reset.

Prerequisites Verification

1. Check Docker Desktop Status

Why important: Docker Desktop must be running before starting any Docker containers. If Docker Desktop is not running, you'll see connection errors even after running docker-compose commands.

# Check if Docker Desktop process is running
Get-Process -Name "Docker Desktop" -ErrorAction SilentlyContinue

# Check Docker CLI connection
docker --version

# If no output or connection errors, start Docker Desktop
# Method 1: Start from Windows Start Menu
# Method 2: Run from PowerShell (try these paths in order):
Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"
Start-Process "C:\Program Files\Docker\Docker Desktop\Docker Desktop.exe"
Start-Process "C:\Program Files\Docker\Desktop\Docker Desktop.exe"

# Wait 1-2 minutes for Docker to fully initialize

2. Verify Cloudflared Installation

Why important: Cloudflare tunnels are required for external access but are started separately from Docker services.

# Check if cloudflared is available
.\cloudflared.exe version

# Verify tunnel configurations exist
ls cloudflared-config.yml, cloudflared-config-vimbiso.yml

Start Production Services

3. Start Docker Production Environment

# Navigate to project directory
cd C:\Great-Sun-Group\credex-core

# Start all production services
docker compose -f docker-compose.prod.yml up -d

# Verify services are starting (this may take several minutes)
docker compose -f docker-compose.prod.yml ps

4. Verify Service Health

Troubleshoot these errors if services fail to start:

# Common errors and solutions:
# Error: unable to get image '...'
# Solution: Docker Desktop not running - start it first (see Prerequisites)

# Error: Access denied or file not found
# Solution: Run PowerShell as Administrator or check permissions

# Warning messages are typically safe:
# - AWS_S3_BACKUP_BUCKET variable not set (expected)
# - BACKUP_WEBHOOK_URL variable not set (expected)
# - Version obsolete warning (informational)

5. Health Check Verification

# Core API Health
curl http://localhost:4000/api-docs

# Expected: HTML content for Swagger UI (200 OK)

# ChatServer Health
curl http://localhost:9000/health/

# Expected: 200 OK with health status

Start Cloudflare Tunnels

6. Check Current Tunnel Status

# Use the provided status checker
.\check-tunnel-status.bat

# Expected: Services should show status 530 (tunnel not running)
# If showing 200 OK, tunnels are already active

7. Start Tunnels for External Access

Important: Tunnel processes run in terminal windows and stop when those windows are closed. Do not close the tunnel windows.

# Start tunnels using provided batch file
.\start-tunnel.bat

# This opens two new terminal windows:
# - Credex tunnel (mycredex.app)
# - Vimbiso tunnel (vimbisopay.africa, vimbisopay.co.zw)

# Keep these windows open for persistent access
# Minimize but DO NOT CLOSE them

8. Verify External Availability

# Re-run status check
.\check-tunnel-status.bat

# Expected results:
# mycredex.app: 301 (redirecting) or 200
# vimbisopay.africa: 200
# vimbisopay.co.zw: Status depends on endpoint but should not be 530

# Test API access through tunnels
curl https://mycredex.app/api-docs

System State Verification

9. Complete System Check

# All containers running and healthy
docker compose -f docker-compose.prod.yml ps

# Expected: 11 containers running, 0 failed

# Service health summary:
# ✓ credex-core-prod
# ✓ vimbiso-chatserver-prod
# ✓ credex-deploy-daemon
# ✓ vimbiso-redis-state-prod
# ✓ credex-neo4j-ledger
# ✓ credex-neo4j-search
# ✓ credex-system-monitor
# ✓ credex-backup-service

10. Deployment System Ready

Once all steps above are confirmed, the system is ready for:

  • GitHub Actions automatic deployments
  • Manual deployment API calls
  • Mobile app deployment and APK downloads

What to Watch For

Common post-restart issues:

  • API returns 503/504 errors after restart: Wait 2-3 minutes for health checks to pass
  • External domains return 530 after tunnel restart: DNS propagation may take 5-10 minutes
  • Container shows Waiting status for several minutes: Normal, wait for health checks

Troubleshooting Failures

If Services Won't Start

# Force restart with cleanup
docker compose -f docker-compose.prod.yml down --remove-orphans
docker compose -f docker-compose.prod.yml up -d

# Check logs for specific errors
docker logs credex-core-prod --tail 20
docker logs vimbiso-chatserver-prod --tail 20

If Tunnels Won't Start

# Kill any existing cloudflared processes
taskkill /F /IM cloudflared.exe

# Verify config files are valid
.\cloudflared.exe tunnel --config cloudflared-config.yml info
.\cloudflared.exe tunnel --config cloudflared-config-vimbiso.yml info

# Start tunnels manually if batch file fails:
start .\cloudflared.exe tunnel --config cloudflared-config.yml run
start .\cloudflared.exe tunnel --config cloudflared-config-vimbiso.yml run

If External Access Still Unavailable

  • Verify DNS configuration in Cloudflare dashboard
  • Check firewall settings for ports 80/443
  • Restart all services in order: Docker → Tunnels → Verification

Architecture

Three Repository Structure

  • credex-core: Main API and backend services
  • vimbiso-chatserver: Chat/messaging service
  • vimbisopay: Flutter mobile application

Daemon and Queue-Based Deployment System

The deployment system uses a queue-based architecture, with a daemon in a seperate container from credex-core but polling a directory it shares with the core, ensuring reliable deployments: 

GitHub Repository → GitHub Actions → Container API → Deployment Queue → Host Daemon → Docker Commands
                                              ↓
                                         202 Accepted
                                      (immediate response)

System Components

  • Container API: Validates tokens, queues deployment requests, returns immediate 202 responses
  • Deployment Queue: File-based queue in /app/source/deploy-queue/ with JSON request files
  • Deployment Daemon: Containerized daemon that monitors queue and executes deployments
  • Blue-Green Deployment: Safe deployment with health checks and automatic rollback

Deployment Process

  1. Request: GitHub Actions calls deployment API
  2. Queue: API creates JSON file in deployment queue and responds immediately
  3. Processing: Daemon detects queue file and starts deployment
  4. Build: New Docker image is built from latest code
  5. Test: New container started on test port for health checking
  6. Switch: After health check passes, production container is replaced
  7. Verify: Final health check on production port
  8. Cleanup: Old containers and temporary files are cleaned up

Deployment Endpoints

All deployment endpoints are hosted at http://localhost:4000 and require authentication via deployment token.

Service Deployment

  • POST /api/deploy-core - Deploy credex-core service
  • POST /api/deploy-chatserver - Deploy vimbiso-chatserver service

Mobile App Deployment

  • POST /api/upload-apk - Upload mobile app APK
  • GET /downloads/vimbisopay-{version}.apk - Download APK files

Version Management (Mobile App)

Version Increment Logic

  • Optional Update (update_required: false): Increment patch version
    • Example: 1.2.3 → 1.2.4
  • Required Update (update_required: true): Increment minor version, reset patch
    • Example: 1.2.3 → 1.3.0

Manual Deployment Process

  1. Navigate to vimbisopay repository on GitHub
  2. Go to Actions → Deploy Mobile App to Local Environment
  3. Click "Run workflow"
  4. Select update type (required/optional)
  5. Enter release notes
  6. Click "Run workflow" to start deployment

Security Configuration

Deployment Token Setup

  1. Generate a secure 32+ character token
  2. Add to GitHub repository secrets as DEPLOY_TOKEN
  3. Configure the same token in local environment variables
  4. All three repositories must have access to this secret

Required Secrets

Each repository needs the following GitHub secret:

  • DEPLOY_TOKEN: Secure deployment authentication token

Best Practices

Development Workflow

  1. Develop and test changes locally
  2. Push to prod branch for automatic deployment (credex-core, vimbiso-chatserver)
  3. Use manual dispatch for mobile app deployments with appropriate update classification
  4. Monitor deployment logs and verify service health after deployment

Version Management

  • Use semantic versioning for all releases
  • Classify updates appropriately (required vs optional)
  • Include meaningful release notes for mobile deployments
  • Test deployments in development environment first

Security

  • Rotate deployment tokens regularly
  • Monitor deployment logs for unauthorized access attempts
  • Keep local production environment secure and updated
  • Use HTTPS in production (configure reverse proxy if needed)

Troubleshooting

System Startup Issues

Docker Desktop Not Running

  • Cause: Docker Desktop must be started before any Docker commands can execute
  • Error Messages: "unable to get image '...' error during connect" or "open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified"
  • Solution: 
    # Check Docker Desktop process
Get-Process -Name "Docker Desktop" -ErrorAction SilentlyContinue

# Start Docker Desktop (try these paths in order):
Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"
Start-Process "C:\Program Files\Docker\Docker Desktop\Docker Desktop.exe"
Start-Process "C:\Program Files\Docker\Desktop\Docker Desktop.exe"

# Wait 1-2 minutes for Docker to fully initialize
timeout /t 120 /nobreak
  • Prevention: Always start Docker Desktop as part of your system startup procedure

Cloudflare Tunnels Stop When Windows Close

  • Cause: Tunnel processes run in interactive terminal windows that persist only while open
  • Symptoms: External domains return "This site can't be reached" (Status 530)
  • Solution: 
    # Restart tunnels
.\start-tunnel.bat

# IMPORTANT: Keep the tunnel windows open!
# Minimize them but do NOT close
  • Prevention: Create persistent tunnel service (requires Windows Administrator privileges): 
    # Attempt service installation (run as Admin)
Start-Process powershell -ArgumentList "& .\cloudflared.exe service install" -Verb RunAs -Wait

# Alternative: Keep tunnel terminals running indefinitely

Access Denied Installing Cloudflared Service

  • Cause: Attempting to install Windows service without administrator privileges
  • Error: "Cannot establish a connection to the service control manager: Access is denied"
  • Solution:
    • Run PowerShell as Administrator
    • Use interactive tunnel mode (keep windows open)
    • Add tunnel startup to system startup scripts

Container Startup Failures After Restart

  • Cause: Services may take 4-5 minutes to fully initialize with health checks
  • Symptoms: Container shows "Waiting" status for extended periods
  • Solution: Wait for health checks to complete. All containers should show "Healthy" status within 4-5 minutes

API Returns 503/504 After Restart

  • Cause: Services still initializing, health checks not yet passed
  • Solution: 
    # Wait and retry health checks
timeout /t 30 /nobreak
curl http://localhost:4000/api-docs
  • Expected Timing: Full system readiness takes 2-5 minutes post-Docker start

Deployment System Issues

Deployment Authentication Failed

  • Cause: Invalid or missing deployment token
  • Solution: Verify DEPLOY_TOKEN secret is set correctly in repository settings

API Connection Failed

  • Cause: Local deployment API not running
  • Solution: Ensure credex-core production environment is running: 
    docker compose -f docker-compose.prod.yml up -d

Deployment Hangs or Times Out

  • Cause: Deployment daemon not processing queue
  • Solution: Check daemon status and restart if needed: 
    # Check daemon status
docker logs credex-deploy-daemon --tail 20

# Restart daemon
docker-compose -f docker-compose.prod.yml restart deploy-daemon

Deployment Fails with Health Check Errors

  • Cause: New container fails to start or respond to health checks
  • Solution: Check container logs and verify application startup: 
    # Check recent deployment logs
docker logs credex-deploy-daemon --tail 50

# Check if containers are running
docker ps --filter "name=credex-core"

Queue Files Not Being Processed

  • Cause: Daemon not monitoring queue directory or permission issues
  • Solution: Verify queue directory and daemon status: 
    # Check queue contents
ls -la deploy-queue/

# Verify daemon is running
docker ps --filter "name=deploy-daemon"

# Check daemon logs
docker logs credex-deploy-daemon --follow

Deployment Succeeds But Website Shows Old Code

  • Cause: Multiple potential issues with git operations or volume mounts
  • Root Causes:
    • Volume mount conflicts between containers
    • Git pulling from local directory instead of remote GitHub repository
    • Docker build cache using old layers
  • Solution: Follow these diagnostic steps: 
    # 1. Verify both containers see the same queue directory
docker exec credex-core-prod ls -la /app/source/deploy-queue/
docker exec credex-deploy-daemon ls -la /app/source/deploy-queue/

# 2. Check deployment logs for git operations
docker logs credex-deploy-daemon --tail 100 | grep -i "git\|clone\|pull"

# 3. Verify git remote configuration in deployment logs
# Look for "From /app/source" (bad) vs "From https://github.com" (good)

# 4. If volume mount issues detected, recreate containers
docker-compose -f docker-compose.prod.yml down credex-core-prod deploy-daemon
docker-compose -f docker-compose.prod.yml up -d credex-core-prod deploy-daemon
  • Prevention: Ensure docker-compose.prod.yml uses consistent volume mounts: 
    # Both containers should use local directory mounts, not named volumes
- ./deploy-queue:/app/source/deploy-queue  # ✅ Correct
- deploy-queue:/app/source/deploy-queue    # ❌ Causes conflicts

If a deployment fails and automatic rollback doesn't work:

# Check for backup containers

# Manual rollback if backup exists
docker stop credex-core-prod
docker rm credex-core-prod
docker rename credex-core-prod-backup credex-core-prod
docker start credex-core-prod

Migration from AWS

Archived Components

The previous AWS-based infrastructure has been archived:

  • Terraform configurations: kept in terraform/ for now.
  • AWS workflows: Moved to terraform/workflows/
  • Documentation: Previous deployment docs preserved for reference

Key Changes

  • No cloud infrastructure: All services run locally
  • Direct deployment: No container registry or ECS deployments
  • Local file storage: APK files stored locally instead of S3
  • Simplified authentication: Single deployment token instead of AWS credentials
