Using Terraform CLI in credex-core

Overview

The credex-core infrastructure is managed using Terraform across multiple environments. While infrastructure changes are typically deployed through GitHub Actions workflows (Connectors, Databases, Application), developers can use the Terraform CLI directly for testing, debugging, or making targeted changes.

IMPORTANT NOTE

The infrastructure is designed to be deployed sequentially in modules that match the workflows, one module at a time. A full teraform deploy destroy the environment's databases and all their data. There probably are not any scenarios in which a full deploy is the solution. Also, it will probably fail.

Environment Structure

Each environment (e.g. development, staging, model_001) has:

  • A dedicated S3 bucket for terraform state: credexbuckets3-statebucket-{environment}
  • Environment-specific AWS credentials
  • Configuration defined in terraform/environments/{environment}.json

Using the Terraform CLI Helper Script

The terraform/tf.sh script simplifies working with Terraform by:

  • Setting up environment-specific AWS credentials
  • Initializing the correct backend configuration
  • Loading required variables

Basic Usage

./tf.sh <environment> <command> [-init]

Parameters:

  • environment: development (default), staging, production, or model_001
  • command: Any terraform command (plan, apply, destroy, etc.)
  • -init: Optional flag to force re-initialization

Examples

# Plan changes in development environment
./tf.sh development plan

# Apply changes to staging
./tf.sh staging apply

# Force reinitialize and plan production
./tf.sh production plan -init

Infrastructure Components

The infrastructure is divided into three main components, each managed by a separate module:

  • Connectors: Core infrastructure (VPC, security groups, load balancers)
  • Databases: Neo4j instances for LedgerSpace and SearchSpace
  • App: ECS service and task definitions

Targeting Specific Components

Use the -target flag to apply changes to specific infrastructure components: 

# Update databases infrastructure
./tf.sh development plan -target=module.databases

# Update core infrastructure (VPC, security groups, etc)
./tf.sh development plan -target=module.connectors

Important Note About App Deployment

The app module should NOT be deployed using terraform apply. Instead:

  • Use terraform only to read infrastructure outputs (Neo4j endpoints, etc)
  • Use AWS CLI directly for app deployment following the process in Application Deployment Workflow
  • This ensures proper handling of task definitions, environment variables, and deployment monitoring

Environment Variables

The full dev environment variables must be available in your development environment, plus AWS secrests in the naming pattern below. (NOTE: this is currently not active and AWS secrets are set in env with no prefix).

  • CREDEXCORE_DEV_AWS_ACCESS_KEY: AWS access key for development environment
  • CREDEXCORE_STAGE_AWS_SECRET_ACCESS_KEY: AWS secret key for staging environment
  • CREDEXCORE_MODEL_001_AWS_ACCESS_KEY: AWS access key for model_001 environment

Best Practices

  • Always run plan before apply to review changes
  • ALWAYS use -target to limit the scope of changes
  • Never use terraform apply for app deployment - use AWS CLI directly
  • Check the GitHub Actions workflows to understand deployment patterns:
    • connectors.yml - Uses terraform for core infrastructure
    • databases.yml - Uses terraform for database instances
    • app.yml - Uses AWS CLI for app deployment
  • Be cautious with destroy commands, especially in production environments

Common Tasks

Viewing Infrastructure State

# List all resources
./tf.sh development show

# Show specific outputs
./tf.sh development output

Debugging Deployments

When debugging deployment issues:

  1. Check the terraform state: 
    ./tf.sh development show
  2. View specific resource details: 
    ./tf.sh development state show module.app.aws_ecs_service.credex_core
  3. Refresh the state to ensure it matches reality: 
    ./tf.sh development refresh
