Same-Server Production Deployment

This document provides a comprehensive guide for deploying the Credex Core production environment alongside your existing development setup on the same Windows server, with integrated MTQ/DCO backup system.

Overview

The same-server production deployment allows you to run both development and production environments on a single Windows machine with complete isolation and comprehensive backup integration. This approach is ideal for:

  • Small to medium-scale deployments (dozens of users)
  • Cost-effective production environments
  • Rapid deployment and testing scenarios
  • Environments where downtime is acceptable for maintenance

Prerequisites

  • Windows 10/11 with Docker Desktop
  • Development environment already running (as per VIMBISO_SETUP_SUMMARY.md)
  • At least 16GB RAM (8GB+ available for production)
  • 100GB+ free disk space
  • Stable internet connection

Resource Management

Production services are configured with resource limits to prevent interference with development:

  • Neo4j instances: 2-3GB memory limit, 1-2 CPU cores each
  • Application services: 512MB-1GB memory limit
  • Total estimated usage: 6-8GB RAM, 4-6 CPU cores

Quick Start Guide

1. Configure Production Environment

Copy and customize the production environment file:

cp .env.prod .env.prod.local

Edit .env.prod.local and replace ALL placeholder values:

Critical Security Keys (MUST CHANGE):

JWT_SECRET_PROD=your-super-secure-jwt-secret-at-least-32-chars
CLIENT_API_KEY_PROD=your-unique-client-api-key-for-production
PASSWORD_PEPPER_PROD=your-password-pepper-for-extra-security
DJANGO_SECRET_PROD=your-django-secret-key-50-chars-minimum

Neo4j License (same as dev):

NEO4J_ENTERPRISE_LICENSE=your_existing_neo4j_license

WhatsApp Production Credentials:

WHATSAPP_API_URL=https://graph.facebook.com/v18.0/
WHATSAPP_ACCESS_TOKEN=your_production_whatsapp_token
WHATSAPP_PHONE_NUMBER_ID=your_production_phone_number_id
WHATSAPP_BUSINESS_ID=your_production_business_account_id

Firebase Production Credentials:

FIREBASE_PROJECT_ID=your-production-firebase-project
FIREBASE_CLIENT_EMAIL=your-production-service-account@project.iam.gserviceaccount.com
FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nYour Production Key\n-----END PRIVATE KEY-----"

2. Start Production Environment

# Start production services
docker compose -f docker-compose.prod.yml --env-file .env.prod.local up -d

# Check service status
docker compose -f docker-compose.prod.yml ps

3. Verify Production Services

Production URLs:

  • Credex Core API: http://localhost:4000
  • Vimbiso ChatServer: http://localhost:9000
  • Neo4j Ledger Browser: http://localhost:7476
  • Neo4j Search Browser: http://localhost:7477
  • System Monitor: http://localhost:9100

Health Checks:

# Test Credex Core
curl http://localhost:4000/api-docs

# Test Vimbiso ChatServer
curl http://localhost:9000/health/

# Test Neo4j connections
docker exec credex-neo4j-ledger-prod cypher-shell -u neo4j -p password "RETURN 'Ledger OK'"
docker exec credex-neo4j-search-prod cypher-shell -u neo4j -p password "RETURN 'Search OK'"

Integrated Backup System

MTQ/DCO Integration

The backup system is fully integrated with your critical business processes:

  • Pre-DCO Backup: Automatic safety snapshot before DCO starts
  • Post-DCO Backup: Captures DCO results and exchange rates
  • Post-MTQ Backup: Transaction logs after MTQ completion
  • Exchange Rate Backup: Immediate backup after ZWG rate fetch

Backup Types & Schedule

Backup Type Schedule Content Retention
Hourly Every 2 hours Transaction logs, Redis state 2 days
Daily 1 AM UTC Full database backup 30 days
Weekly Sunday 2 AM UTC Complete system backup 12 weeks
Maintenance Midnight UTC Full backup + system maintenance 7 days
Post-MTQ After MTQ completion Transaction logs, state 2 days
Post-DCO After DCO completion Full backup + exchange rates 30 days

Manual Backup Commands

# Trigger manual backups
docker exec credex-backup-service /scripts/integrated-backup.sh daily
docker exec credex-backup-service /scripts/integrated-backup.sh maintenance

# Check backup logs
docker logs credex-backup-service

# List backup files
ls -la ./backups/

Backup Locations

  • Local: ./backups/ directory
  • Cloud: AWS S3 (if configured)
  • Structure:
    • ./backups/hourly/ - Hourly backups
    • ./backups/daily/ - Daily backups
    • ./backups/weekly/ - Weekly backups
    • ./backups/maintenance/ - Maintenance backups
    • ./backups/post-mtq/ - Post-MTQ backups
    • ./backups/post-dco/ - Post-DCO backups
    • ./backups/exchange-rates/ - Exchange rate data

Daily Operations

Morning Checklist

  1. Check service health: docker compose -f docker-compose.prod.yml ps
  2. Review backup logs: docker logs credex-backup-service --tail 50
  3. Check disk space: df -h
  4. Monitor system resources: Visit http://localhost:9100

Maintenance Window (Midnight UTC)

The system automatically performs comprehensive maintenance during the daily DCO window:

  • Full system backup with consistent snapshots
  • Docker system cleanup
  • Log rotation and cleanup
  • Database optimization
  • System health checks

Performance Considerations

Resource Contention

High Impact Activities:

  • Visual Studio/VS Code with large projects
  • Database management tools
  • Docker builds
  • File indexing (Windows Search, antivirus)

Mitigation Strategies:

  • Resource limits on production containers
  • Separate Docker networks for isolation
  • Backup scheduling during low-usage periods
  • Process-aware backup system (waits for MTQ/DCO completion)

System Requirements

Minimum for Dev + Prod:

  • RAM: 16GB (8GB might work but will be tight)
  • CPU: 4+ cores (8+ preferred)
  • Storage: SSD with 100GB+ free space
  • Network: Stable broadband with decent upload

Troubleshooting

Service Won't Start

# Check logs
docker logs credex-core-prod
docker logs vimbiso-chatserver-prod

# Check resource usage
docker stats

# Restart specific service
docker compose -f docker-compose.prod.yml restart credex-core-prod

Backup Issues

# Check backup service logs
docker logs credex-backup-service

# Manual backup test
docker exec credex-backup-service /scripts/integrated-backup.sh daily

# Check backup directory
ls -la ./backups/

Database Connection Issues

# Test Neo4j connections
docker exec credex-neo4j-ledger-prod cypher-shell -u neo4j -p password "RETURN datetime()"

# Check Redis
docker exec vimbiso-redis-state-prod redis-cli ping

Security Considerations

Network Isolation

  • Production and development use separate Docker networks
  • No cross-contamination between environments
  • Firewall configuration for external access

Data Protection

  • All production secrets in separate .env file
  • Regular automated backups with encryption
  • Transaction-level backup integration
  • Backup integrity verification

Migration Path to Cloud

When to Consider Migration

  • More than 100 concurrent users
  • Need for high availability
  • Geographic distribution required
  • Compliance requirements

Migration Strategy

  • Terraform configurations already exist for AWS
  • Backup system supports S3 upload
  • Database dumps are portable
  • Gradual migration possible

Conclusion

The same-server production deployment provides a robust, cost-effective solution for running production workloads alongside development environments. The integrated backup system ensures comprehensive data protection with minimal operational overhead, while the process-aware backup triggers provide maximum protection during critical business operations like MTQ and DCO processing.

This deployment model is particularly well-suited for organizations that prioritize data protection over high availability and can accept scheduled maintenance windows for comprehensive system maintenance.
