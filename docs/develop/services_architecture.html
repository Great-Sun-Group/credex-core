Services Architecture

Modular Service-Based Architecture

The Credex API implements a modular service-based architecture that separates business logic from controllers, promoting code reuse, maintainability, and extensibility. This document outlines the service architecture, its organization, and best practices for using and creating services.

Service Categories

Services are organized into categories based on their purpose and domain. Each category has its own directory under src/services/.

AssetMarker Services

Located in /services/assetMarker/, these services handle the creation, retrieval, updating, and deletion of asset markers in the system.

  • assetMarkerService.ts: Provides methods for managing asset markers, including creating single and multiple asset markers, finding or creating accounts, and handling image assets.

Relationship Services

Located in /services/relationships/, these services manage relationships between nodes in the Neo4j database.

  • relationshipService.ts: Provides methods for connecting and disconnecting assets to other nodes, checking if relationships exist, and retrieving relationships.

Transformation Services

Located in /services/transformations/, these services handle data transformations and can be shared with other members.

  • imageProcessingService.ts: Provides methods for processing images, including resizing, optimizing, and creating different versions of images.

Service Design Principles

The service architecture follows these key design principles:

1. Separation of Concerns

Services separate business logic from controllers, allowing controllers to focus on request handling, validation, and response formatting. This separation makes the code more maintainable and testable.

    // Process the image using the service

2. Reusability

Services are designed to be reusable across multiple controllers and use cases. This reduces code duplication and ensures consistent behavior across the application.

3. Single Responsibility

Each service has a single responsibility and focuses on a specific domain. This makes services easier to understand, test, and maintain.

4. Dependency Injection

Services receive dependencies like database sessions as parameters rather than creating them internally. This makes services more testable and allows for better resource management.

5. Error Handling

Services include proper error handling and logging to aid in debugging and monitoring. Errors are caught, logged, and rethrown to be handled by the calling code.

Error Handling Example

public async someMethod(param1: string, param2: number): Promise {
  try {
    // Implementation
    logInfo("Method called", {
      service: "SomeService",
      method: "someMethod",
      param1,
      param2
    });
    
    return result;
  } catch (error) {
    logError("Error in method", error instanceof Error ? error : new Error(String(error)), {
      service: "SomeService",
      method: "someMethod",
      error: error instanceof Error ? error.message : String(error)
    });
    throw error;
  }
}

Using Services

Services are designed to be used by controllers to implement API endpoints. Here's how to use a service in a controller:

  1. Import the service from its module: 
    import { assetMarkerService } from "../../../services/assetMarker/assetMarkerService";
  2. Create a database session (if needed): 
    const session = ledgerSpaceDriver.session();
  3. Use the service methods within a try/catch block: 
    try {
  const result = await assetMarkerService.someMethod(session, ...);
  // Use the result
} catch (error) {
  // Handle the error
} finally {
  await session.close();
}

Creating New Services

When creating a new service, follow these guidelines:

  1. Categorize: Place the service in the appropriate category directory based on its purpose.
  2. Single Responsibility: Each service should have a single responsibility and focus on a specific domain.
  3. Reusability: Design services to be reusable across multiple controllers.
  4. Error Handling: Include proper error handling and logging in service methods.
  5. Documentation: Document the service's purpose, methods, and parameters.

Transformation Services as User-Generated Services

Transformation services are designed to be potentially user-generated and shareable. These services can be used to transform data in various ways and can be made available to other members.

The imageProcessingService is an example of a transformation service that could be shared with other members. It provides methods for processing images, including resizing, optimizing, and creating different versions of images.

When creating a transformation service, consider:

  1. Modularity: Design the service to be modular and self-contained.
  2. Configuration: Allow for configuration options to customize the transformation.
  3. Input/Output: Clearly define the expected input and output formats.
  4. Documentation: Provide clear documentation on how to use the service.

Best Practices

Follow these best practices when working with services:

  1. Use Dependency Injection: Pass dependencies like database sessions to service methods rather than creating them inside the service.
  2. Validate Inputs: Validate inputs to service methods to ensure they are valid before performing operations.
  3. Return Meaningful Results: Return meaningful results from service methods, including success/failure indicators and relevant data.
  4. Log Operations: Log important operations and errors to aid in debugging and monitoring.
  5. Handle Errors: Handle errors gracefully and provide meaningful error messages.
  6. Use Interfaces: Define interfaces for service parameters and return values to ensure type safety.
  7. Write Tests: Write tests for service methods to ensure they work as expected.

Testing Services

Services should be tested independently of controllers to ensure they work as expected. Here's an example of how to test a service:

Example Service Test

import { assetMarkerService } from "../../../src/services/assetMarker/assetMarkerService";

describe("AssetMarkerService", () => {
  let mockSession: any;

  beforeEach(() => {
    // Create a mock session
    mockSession = {
      executeRead: jest.fn(),
      executeWrite: jest.fn(),
      close: jest.fn()
    };
  });

  describe("createSingleAssetMarker", () => {
    it("should create a single asset marker", async () => {
      // Arrange
      const assetProps = { assetName: "Test Asset" };
      const crAccount = { accountID: "cr-account-id", amount: 100 };
      const drAccount = { accountID: "dr-account-id", amount: 100 };
      
      mockSession.executeWrite.mockResolvedValue({
        records: [{ get: () => ({ properties: { id: "asset-id" } }) }]
      });

      // Act
      const result = await assetMarkerService.createSingleAssetMarker(
        mockSession, assetProps, crAccount, drAccount
      );

      // Assert
      expect(result).toBe("asset-id");
      expect(mockSession.executeWrite).toHaveBeenCalled();
    });
  });
});
