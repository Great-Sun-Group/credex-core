Mathematical logic and conceptual specifics

MinuteTransactionQueue (MTQ)

The Minute Transaction Queue (MTQ) is a central component of the Credexecosystem that runs every minute. It links the main ledgerSpace database (the source of truth and full information) to a searchSpace database (optimized to find credloops). Every minute, first any new accounts are added to the searchSpace, then any new credexes. After each new credex is added, the ecosystem finds and clears all possible loops created by the new credex before moving on to the next.

MinuteTransactionQueue Process

The MinuteTransactionQueue runs as a cron job every minute, with several safety mechanisms:

  1. Status Checks:
    • Verifies no DCO (Daily Credcoin Offering) is in progress
    • Ensures no other MTQ process is currently running
    • Sets an MTQ running flag to prevent concurrent processing
  2. Safety Mechanisms:
    • 14-minute bail timer to prevent infinite processing
    • Comprehensive error handling and logging
    • Automatic cleanup of running flags
    • Session management for both ledgerSpace and searchSpace databases
  3. Account Processing:
    • Identifies accounts with "PENDING_ACCOUNT" status
    • Creates corresponding accounts in searchSpace
    • Updates status to "PROCESSED" in ledgerSpace
    • Handles each account independently to isolate failures
  4. Credex Processing:
    • Retrieves credexes with "PENDING_CREDEX" status
    • Sorts by acceptance time to maintain transaction order
    • Processes each credex through the LoopFinder
    • Handles secured and unsecured credexes differently

LoopFinder Architecture

The LoopFinder handles both unsecured and secured credexes. It manages the creation, processing, and clearing of credex loops while maintaining data integrity across both the searchSpace and ledgerSpace databases.

Core Components

  • LoopFinder.ts: Main orchestrator that:
    • Manages database sessions for both spaces
    • Coordinates the loop finding and processing workflow
    • Implements comprehensive error handling and logging
    • Ensures proper cleanup of resources
  • LoopFinderDB.ts: Database operations including:
    • Creating and managing credexes in searchSpace
    • Finding potential credloops using graph traversal
    • Cleaning up searchSpace after loop processing
    • Updating ledgerSpace with loop results
  • LoopFinderUtils.ts: Utility functions for:
    • Determining search relationship types
    • Adjusting credex due dates for secured credexes
    • Managing type conversions and validations

Secured vs Unsecured Credexes

The system handles two types of credexes:

  • Unsecured Credexes:
    • Use standard "UNSECURED" relationship type
    • Maintain their original due dates
    • Follow normal loop finding paths
  • Secured Credexes:
    • Use denomination-specific relationship types (e.g., "USD_SECURED", "EUR_SECURED")
    • Due dates are automatically adjusted to the current day
    • Maintain separate loop paths from unsecured credexes
    • Require additional validation and security checks

Search Space Architecture

The searchSpace is optimized for efficient loop finding:

  1. Search Anchors:
    • Act as intermediaries between accounts
    • Maintain the earliest due date among connected credexes
    • Separate paths by relationship type (secured vs unsecured)
    • Automatically created and removed as needed
  2. Credex Nodes:
    • Store essential credex information:
      • Outstanding amount
      • Denomination
      • CXX multiplier
      • Due date
    • Connect to search anchors via SEARCH_SECURED relationships
    • Updated in real-time as loops are cleared
  3. Relationship Management:
    • Automatic creation of required relationships
    • Dynamic updates of search anchor properties
    • Cleanup of orphaned relationships
    • Maintenance of relationship metadata

Loop Finding Algorithm

  1. Loop Discovery:
    • Uses Cypher path finding to identify potential loops
    • Filters paths based on relationship types
    • Prioritizes loops with earliest due dates
    • Handles ties using amount-based prioritization
  2. Loop Validation:
    • Verifies all credexes are still valid
    • Checks relationship types match throughout the loop
    • Validates denomination compatibility
    • Ensures proper due date ordering
  3. Loop Processing:
    • Calculates minimum clearable amount
    • Updates all credexes atomically
    • Creates loop documentation in ledgerSpace
    • Manages relationship transitions
  4. Cleanup Operations:
    • Removes fully cleared credexes
    • Updates search anchor properties
    • Cleans up orphaned relationships
    • Maintains data consistency

Error Handling and Recovery

The system implements comprehensive error handling:

  • Transaction Management:
    • All database operations use managed sessions
    • Automatic rollback on failures
    • Proper cleanup of resources
    • Session isolation for concurrent operations
  • Error Logging:
    • Detailed error messages with context
    • Stack traces for debugging
    • Operation-specific logging
    • Performance metrics tracking
  • Recovery Mechanisms:
    • Failed operations can be retried
    • Automatic cleanup of incomplete states
    • Monitoring of system health
    • Alerts for critical failures

This implementation actualizes the Credex Principle by finding loops where "If I owe you, and you owe them, and they owe me, we're square." It automatically clears these loops, reducing the outstanding amounts of all involved credexes by the same amount (the minimum amount in the loop). The differentiates between unsecured and secured credexes in every denomination, maintaining separate paths and applying different rules as needed.
