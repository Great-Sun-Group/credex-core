Logging Configuration

Overview of the credex-core Logging System

The credex-core application uses a structured logging system built on Winston to provide consistent, configurable logging across different environments. This document explains how logging is configured, how to control log levels, and best practices for logging in different deployment environments.

Log Levels

The application supports the following log levels, in order of increasing verbosity:

  • error: Critical errors that require immediate attention
  • warn: Warning conditions that should be addressed
  • info: Informational messages about normal operation
  • http: HTTP request/response details
  • verbose: Detailed operational information
  • debug: Debugging information for development
  • silly: Extremely detailed debugging information

Environment-Based Configuration

By default, the log level is determined based on the NODE_ENV environment variable:

  • development: Uses debug level for verbose logging
  • production: Uses info level for standard operational logging
  • staging: Follows the same pattern as development (debug level)
  • test: Follows the same pattern as development (debug level)

Overriding Log Levels

You can override the default log level by setting the LOG_LEVEL environment variable. This takes precedence over the environment-based defaults.

Examples:


# Set debug level logging in any environment
LOG_LEVEL=debug

# Set info level logging in any environment
LOG_LEVEL=info

# Set error-only logging for minimal output
LOG_LEVEL=error

Configuration in Different Environments

Local Development

For local development, you can set the log level when starting the application: 


LOG_LEVEL=debug npm run dev

Docker Development

When using Docker Compose for development, the log level is set in docker-compose.dev.yml: 


environment:
  NODE_ENV: ${NODE_ENV:-development}
  LOG_LEVEL: ${LOG_LEVEL:-debug}

You can override this when starting Docker Compose: 


LOG_LEVEL=info docker-compose -f docker-compose.dev.yml up

Deployed Environments

In deployed environments, we explicitly set the LOG_LEVEL environment variable in the ECS task definition rather than relying on NODE_ENV-based defaults:

  • Development: LOG_LEVEL=debug for verbose logging in the development environment
  • Production: LOG_LEVEL=info for standard operational logging in the production environment

These settings are configured in the Terraform infrastructure code and can be modified if needed.

Log Output

Logs are output in different formats depending on the environment:

  • Console: All environments log to the console/stdout
  • Files: Production environment also logs to rotating files:
    • logs/error-%DATE%.log: Error-level logs only
    • logs/combined-%DATE%.log: All logs
  • CloudWatch: In AWS deployments, logs are sent to CloudWatch Logs

Best Practices

  • Use debug level for development environments to get detailed information
  • Use info level for production to reduce noise while maintaining operational visibility
  • For troubleshooting specific issues in production, temporarily increase the log level to debug
  • Remember that sensitive information is automatically redacted from logs
  • Large request/response bodies are truncated in logs to prevent excessive log size

Viewing Logs

Local Development

Logs are output to the console during local development.

AWS Deployments

For AWS deployments, logs can be viewed in CloudWatch Logs or using the aws/fetchlogs.js utility: 


# Stream logs in real-time
node aws/fetchlogs.js

# Fetch the last 5 minutes of logs
node aws/fetchlogs.js 300
