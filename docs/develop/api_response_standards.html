API Response Standards

The credex-core API follows standardized patterns for all responses to ensure consistency and predictability. This document outlines these standards and explains how responses are structured.

Response Structure

All API responses follow this standard structure:

{
  "message": "Human-readable description of the operation result",
  "data": {
    "action": {
      "id": "UUID of the affected resource",
      "type": "Type of action performed",
      "timestamp": "ISO date-time of the action",
      "actor": "UUID of the member who performed the action",
      "details": {
        // Action-specific details
      }
    },
    "dashboard": {
      // Current state information
    }
  }
}

Message Field

The message field provides a human-readable description of what occurred. It should be:

  • Clear and concise
  • Action-oriented (e.g., "Account created successfully")
  • Helpful for debugging in error cases

Action Object

The action object records what operation was performed:

  • id: UUID of the primary resource affected (may be null for some operations)
  • type: Standardized action type (e.g., ACCOUNT_CREATED, ERROR_VALIDATION)
  • timestamp: When the action occurred (ISO 8601 format)
  • actor: Who performed the action (member UUID or "system")
  • details: Action-specific information about what changed

Dashboard Structure

The dashboard object provides the current state after an operation. Its structure is defined in src/types/dashboardSwaggerTemplate.ts and includes:

Member Information

  • Authentication Context
    • memberID (UUID)
    • memberTier (integer)
    • remainingAvailableUSD (number, optional)
  • Personal Details
    • firstname and lastname
    • memberHandle
    • defaultDenom

Account Information

  • Account List
    • Basic details (ID, name, handle, type)
    • Ownership and authorization status
    • Default denomination
  • Balance Data
    • Secured balances by denomination
    • Unsecured balances in default denomination
    • Net Credex assets
  • Pending Transactions
    • Incoming transactions
    • Outgoing transactions

Dashboard Response Patterns

The API uses three main patterns for dashboard responses:

1. Full Dashboard State

Returned by operations that modify state:

  • Authentication operations
  • Account management
  • Transaction operations

2. Empty Dashboard

Used for operations that don't affect state:

  • Lookup operations
  • Validation checks
  • Authorization checks

3. Specialized Dashboard

Contains additional context-specific data:

  • Transaction history (getLedger)
  • Recurring transaction details
  • Specialized balance views

Error Responses

Error responses maintain the same structure but with specific patterns:

  • HTTP Status Codes
    • 400: Invalid input or validation error
    • 401: Authentication required
    • 403: Permission denied
    • 404: Resource not found
    • 409: Conflict with existing resource
    • 500: Internal server error
  • Error Action Types
    • ERROR_VALIDATION: Input validation failures
    • ERROR_UNAUTHORIZED: Authentication/authorization failures
    • ERROR_NOT_FOUND: Resource lookup failures
    • ERROR_INTERNAL: System errors
  • Error Details
    • code: Specific error code
    • reason: Detailed error explanation
    • field: Affected field (for validation errors)
    • suggestion: Recommended fix (when applicable)

Implementation Notes

When implementing API endpoints:

  • Use consistent property names and types
  • Include proper validation and error handling
  • Document all possible responses in swagger
  • Maintain proper denomination formatting
  • Use UUIDs for resource identification
  • Include proper security headers
  • Log appropriate debugging information

For detailed specifications of the dashboard format and all available fields, refer to dashboardSwaggerTemplate in src/types/dashboardSwaggerTemplate.ts.
