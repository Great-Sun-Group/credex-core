Repository Architecture

The credex-core API uses a repository pattern to abstract database operations and optimize data access. This document outlines the key repositories and their usage patterns.

Member Repositories

MemberRepository

Handles member data retrieval with optimizations for dashboard operations:

  • Key Methods
    • findById: Retrieves member data with tier and preferences
    • findByPhone: Retrieves member data for authentication
  • Optimizations
    • Result caching with 30-second TTL
    • Single query pattern for all member data
    • Proper indexing on memberID and phone
  • Usage Example 
    const memberRepo = new MemberRepository();
const memberData = await memberRepo.findById(memberID);
if (memberData) {
  // Access member properties
  const { tier, firstname, lastname, handle, defaultDenom } = memberData;
}

SpendLimitRepository

Manages tier-specific spend limit calculations:

  • Key Methods
    • getRemainingLimit: Calculates available spend based on tier and usage
    • getCurrentMonthUsage: Tracks month-to-date spend
  • Optimizations
    • Cached calculations with short TTL
    • Efficient date-based queries
    • Proper indexing on transaction dates

Account Repositories

AccountRepository

Manages account data and access control:

  • Key Methods
    • findByIdWithAccess: Gets account data with authorization check
    • findAccessibleAccountIds: Lists accounts a member can access
  • Optimizations
    • Combined authorization and data queries
    • Result caching with member-specific keys
    • Proper indexing on accountID and relationships
  • Usage Example 
    const accountRepo = new AccountRepository();
const accountData = await accountRepo.findByIdWithAccess(accountID, memberID);
if (accountData) {
  // Access account properties
  const { accountName, accountType, defaultDenom, isOwnedAccount } = accountData;
}

BalanceRepository

Handles complex balance calculations across denominations:

  • Key Methods
    • getBalances: Retrieves comprehensive balance data
    • getSecuredBalances: Gets secured credex balances by denomination
    • getUnsecuredBalances: Gets unsecured credex totals
  • Optimizations
    • Efficient balance aggregation queries
    • Result caching with account-specific keys
    • Proper indexing on credex relationships
  • Usage Example 
    const balanceRepo = new BalanceRepository();
const balanceData = await balanceRepo.getBalances(accountID);
const {
  securedNetBalancesByDenom,
  unsecuredBalancesInDefaultDenom,
  netCredexAssetsInDefaultDenom
} = balanceData;

Implementation Notes

Repository Initialization

Repositories should be initialized at the service level and passed to controllers: 

// Initialize repositories
const memberRepo = new MemberRepository();
const spendLimitService = new SpendLimitService();

// Initialize services with repositories
const memberDashboardService = new MemberDashboardService(
  memberRepo,
  spendLimitService
);

Error Handling

Repositories use standardized error handling:

  • Database errors are wrapped in domain-specific errors
  • Not found conditions return null rather than throwing
  • Authorization failures are handled at the service level

Caching Strategy

All repositories implement consistent caching:

  • 30-second TTL for standard operations
  • Cache keys include all relevant identifiers
  • Cache clearing methods for both specific and full clear
  • Automatic cache updates on write operations

Query Optimization

Repositories follow these optimization principles:

  • Single query pattern for related data
  • Proper use of Neo4j indexes
  • Efficient relationship traversal
  • Minimal data transformation in memory
