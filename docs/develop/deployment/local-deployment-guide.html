Local CI/CD Pipeline Deployment Guide

This guide covers the local deployment system that replaced previous AWS-based infrastructure.

Overview

The local CI/CD pipeline automatically deploys services to the local production environment using GitHub Actions workflows that call deployment APIs running on the local server.

Architecture

Three Repository Structure

  • credex-core: Main API and backend services
  • vimbiso-chatserver: Chat/messaging service
  • vimbisopay: Flutter mobile application

Daemon and Queue-Based Deployment System

The deployment system uses a queue-based architecture, with a daemon in a seperate container from credex-core but polling a directory it shares with the core, ensuring reliable deployments: 

GitHub Repository → GitHub Actions → Container API → Deployment Queue → Host Daemon → Docker Commands
                                              ↓
                                         202 Accepted
                                      (immediate response)

System Components

  • Container API: Validates tokens, queues deployment requests, returns immediate 202 responses
  • Deployment Queue: File-based queue in /app/source/deploy-queue/ with JSON request files
  • Deployment Daemon: Containerized daemon that monitors queue and executes deployments
  • Blue-Green Deployment: Safe deployment with health checks and automatic rollback

Deployment Process

  1. Request: GitHub Actions calls deployment API
  2. Queue: API creates JSON file in deployment queue and responds immediately
  3. Processing: Daemon detects queue file and starts deployment
  4. Build: New Docker image is built from latest code
  5. Test: New container started on test port for health checking
  6. Switch: After health check passes, production container is replaced
  7. Verify: Final health check on production port
  8. Cleanup: Old containers and temporary files are cleaned up

Deployment Endpoints

All deployment endpoints are hosted at http://localhost:4000 and require authentication via deployment token.

Service Deployment

  • POST /api/deploy-core - Deploy credex-core service
  • POST /api/deploy-chatserver - Deploy vimbiso-chatserver service

Mobile App Deployment

  • POST /api/upload-apk - Upload mobile app APK
  • GET /downloads/vimbisopay-{version}.apk - Download APK files

GitHub Actions Workflows

1. credex-core Repository

  • File: .github/workflows/deploy-local.yml
  • Trigger: Automatic on push to prod branch
  • Actions:
    • Checkout code
    • Call deployment API with service details
    • Verify deployment success
    • Report status and create artifacts

2. vimbiso-chatserver Repository

  • File: .github/workflows/deploy-local.yml
  • Trigger: Automatic on push to prod branch
  • Actions:
    • Checkout code
    • Call deployment API with service details
    • Verify deployment success
    • Report status and create artifacts

3. vimbisopay Repository

  • File: .github/workflows/deploy-mobile.yml
  • Trigger: Manual workflow dispatch
  • Actions:
    • Setup Flutter environment
    • Run tests and build APK
    • Auto-increment version based on update type
    • Upload APK to deployment API
    • Verify availability and commit version update

Version Management (Mobile App)

Version Increment Logic

  • Optional Update (update_required: false): Increment patch version
    • Example: 1.2.3 → 1.2.4
  • Required Update (update_required: true): Increment minor version, reset patch
    • Example: 1.2.3 → 1.3.0

Manual Deployment Process

  1. Navigate to vimbisopay repository on GitHub
  2. Go to Actions → Deploy Mobile App to Local Environment
  3. Click "Run workflow"
  4. Select update type (required/optional)
  5. Enter release notes
  6. Click "Run workflow" to start deployment

Security Configuration

Deployment Token Setup

  1. Generate a secure 32+ character token
  2. Add to GitHub repository secrets as DEPLOY_TOKEN
  3. Configure the same token in local environment variables
  4. All three repositories must have access to this secret

Required Secrets

Each repository needs the following GitHub secret:

  • DEPLOY_TOKEN: Secure deployment authentication token

Best Practices

Development Workflow

  1. Develop and test changes locally
  2. Push to prod branch for automatic deployment (credex-core, vimbiso-chatserver)
  3. Use manual dispatch for mobile app deployments with appropriate update classification
  4. Monitor deployment logs and verify service health after deployment

Version Management

  • Use semantic versioning for all releases
  • Classify updates appropriately (required vs optional)
  • Include meaningful release notes for mobile deployments
  • Test deployments in development environment first

Security

  • Rotate deployment tokens regularly
  • Monitor deployment logs for unauthorized access attempts
  • Keep local production environment secure and updated
  • Use HTTPS in production (configure reverse proxy if needed)

Troubleshooting

Deployment System Issues

Deployment Authentication Failed

  • Cause: Invalid or missing deployment token
  • Solution: Verify DEPLOY_TOKEN secret is set correctly in repository settings

API Connection Failed

  • Cause: Local deployment API not running
  • Solution: Ensure credex-core production environment is running: 
    docker compose -f docker-compose.prod.yml up -d

Deployment Hangs or Times Out

  • Cause: Deployment daemon not processing queue
  • Solution: Check daemon status and restart if needed: 
    # Check daemon status
docker logs credex-deploy-daemon --tail 20

# Restart daemon
docker-compose -f docker-compose.prod.yml restart deploy-daemon

Deployment Fails with Health Check Errors

  • Cause: New container fails to start or respond to health checks
  • Solution: Check container logs and verify application startup: 
    # Check recent deployment logs
docker logs credex-deploy-daemon --tail 50

# Check if containers are running
docker ps --filter "name=credex-core"

Queue Files Not Being Processed

  • Cause: Daemon not monitoring queue directory or permission issues
  • Solution: Verify queue directory and daemon status: 
    # Check queue contents
ls -la deploy-queue/

# Verify daemon is running
docker ps --filter "name=deploy-daemon"

# Check daemon logs
docker logs credex-deploy-daemon --follow

Deployment Succeeds But Website Shows Old Code

  • Cause: Multiple potential issues with git operations or volume mounts
  • Root Causes:
    • Volume mount conflicts between containers
    • Git pulling from local directory instead of remote GitHub repository
    • Docker build cache using old layers
  • Solution: Follow these diagnostic steps: 
    # 1. Verify both containers see the same queue directory
docker exec credex-core-prod ls -la /app/source/deploy-queue/
docker exec credex-deploy-daemon ls -la /app/source/deploy-queue/

# 2. Check deployment logs for git operations
docker logs credex-deploy-daemon --tail 100 | grep -i "git\|clone\|pull"

# 3. Verify git remote configuration in deployment logs
# Look for "From /app/source" (bad) vs "From https://github.com" (good)

# 4. If volume mount issues detected, recreate containers
docker-compose -f docker-compose.prod.yml down credex-core-prod deploy-daemon
docker-compose -f docker-compose.prod.yml up -d credex-core-prod deploy-daemon
  • Prevention: Ensure docker-compose.prod.yml uses consistent volume mounts: 
    # Both containers should use local directory mounts, not named volumes
- ./deploy-queue:/app/source/deploy-queue  # ✅ Correct
- deploy-queue:/app/source/deploy-queue    # ❌ Causes conflicts

Mobile App Issues

Mobile App Build Failed

  • Cause: Flutter build errors or missing dependencies
  • Solution: Check workflow logs for specific Flutter errors

Version Increment Failed

  • Cause: Invalid version format in pubspec.yaml
  • Solution: Ensure version follows semantic versioning (x.y.z format)

Deployment Daemon Management

Monitor Daemon Status

# Check if daemon container is running
docker ps --filter "name=deploy-daemon"

# View real-time daemon logs
docker logs credex-deploy-daemon --follow

# Check daemon heartbeat (should show every minute)
docker logs credex-deploy-daemon --tail 10 | grep "heartbeat"

Restart Deployment System

# Restart just the daemon
docker-compose -f docker-compose.prod.yml restart deploy-daemon

# Restart entire production environment
docker-compose -f docker-compose.prod.yml down
docker-compose -f docker-compose.prod.yml up -d

Manual Deployment Testing

# Test deployment API directly
curl -X POST http://localhost:4000/api/deploy-core \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_DEPLOY_TOKEN" \
  -d '{"branch": "prod"}'

# Check queue after API call
ls -la deploy-queue/

Emergency Rollback

If a deployment fails and automatic rollback doesn't work:

# Check for backup containers
docker ps -a --filter "name=credex-core-prod-backup"

# Manual rollback if backup exists
docker stop credex-core-prod
docker rm credex-core-prod
docker rename credex-core-prod-backup credex-core-prod
docker start credex-core-prod

Health Checks

Verify Deployment API

curl http://localhost:4000/api-docs

Verify ChatServer

curl http://localhost:9000/health/

Check Service Status

docker compose -f docker-compose.prod.yml ps

Monitoring

  • APK files (for mobile deployments)

Logs

  • GitHub Actions: View workflow logs in repository Actions tab
  • Local Services: Use Docker logs to monitor service deployment 
    docker logs credex-core-prod --tail 50
docker logs vimbiso-chatserver-prod --tail 50

Migration from AWS

Archived Components

The previous AWS-based infrastructure has been archived:

  • Terraform configurations: kept in terraform/ for now.
  • AWS workflows: Moved to terraform/workflows/
  • Documentation: Previous deployment docs preserved for reference

Key Changes

  • No cloud infrastructure: All services run locally
  • Direct deployment: No container registry or ECS deployments
  • Local file storage: APK files stored locally instead of S3
  • Simplified authentication: Single deployment token instead of AWS credentials
