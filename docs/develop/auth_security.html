Security and Authentication Overview

This document provides a comprehensive overview of the core security infrastructure and mechanisms implemented in our application. For business-specific security features related to Credex transactions, secured authorizations, and tier-based limits, please refer to the Business Security Features.

Authentication System

JWT Authentication

Our application uses JSON Web Tokens (JWT) for authentication, with several security measures to ensure token integrity and proper lifecycle management:

Token Generation and Structure

  • Tokens contain:
    • memberID - Unique identifier for the authenticated member
    • iat (Issued At) - Token creation timestamp
    • lastActivity - Timestamp of last valid request
    • absoluteExpiry - Hard expiration timestamp
  • Tokens are signed using JWT_SECRET environment variable
  • Token verification includes signature and expiration checks

Token Lifecycle

  • Activity-based expiration:
    • Tokens expire after 5 minutes of inactivity
    • Each valid request refreshes the activity timer
    • Prevents token reuse after periods of inactivity
  • Absolute expiration:
    • Maximum token age of 6 hours
    • Not extended by activity or refresh
    • Forces periodic re-authentication
  • Token refresh:
    • New token issued with each valid request
    • Maintains original absolute expiry time
    • Returned in Authorization header

Member Verification

  • Database verification on every request:
    • Confirms member still exists
    • Validates member status
    • Attaches current member properties to request
  • Failed verification scenarios:
    • Member not found - Token invalidated
    • Invalid token signature - 401 response
    • Token expired - 401 response with reason

Client API Key Authentication

Used for keyhole endpoints that need to operate without JWT authentication:

  • Implementation:
    • Required header: x-client-api-key
    • Matches against CLIENT_API_KEY environment variable
    • Used for /v1/login and /v1/onboardMember routes
  • Security measures:
    • Key verification on every request
    • 500 error if environment variable not set
    • 401 response for invalid/missing keys
    • Detailed security logging

Helmet Security Headers

Comprehensive HTTP header security through Helmet middleware:

Development Environment

  • Content Security Policy (CSP):
    • defaultSrc: 'self' - Restrict resource loading to same origin
    • scriptSrc: 'self', 'unsafe-inline' - Control script sources
    • styleSrc: 'self', 'unsafe-inline' - Control style sources
    • imgSrc: 'self', data: - Control image sources
    • fontSrc: 'self' - Control font loading
    • frameAncestors: 'self' - Prevent clickjacking
    • formAction: 'self' - Control form submissions
  • HTTP Strict Transport Security (HSTS):
    • maxAge: 31536000 (1 year)
    • includeSubDomains: true
    • preload: true
  • Additional Headers:
    • Referrer-Policy: strict-origin-when-cross-origin
    • X-Content-Type-Options: nosniff
    • X-Frame-Options: SAMEORIGIN
    • X-XSS-Protection: 1; mode=block

CORS Configuration

Development Environment

  • Permissive configuration:
    • origin: '*' - Allow all origins
    • methods: POST only
    • allowedHeaders: Content-Type, Authorization, x-client-api-key, x-dev-admin-key, x-skip-rate-limit
    • credentials: true - Allow credentials
    • maxAge: 86400 - Cache preflight for 1 day

Production Environment

  • Strict security rules:
    • HTTPS required for all origins
    • Blocked protocols: file://, data://
    • Blocked sources: localhost, IP addresses
    • Origin validation with security checks
    • Same methods and headers as development
    • Credentials allowed with proper origin checks

Rate Limiting

Standard Rate Limiting

  • Configuration:
    • Window: 60 seconds (rolling)
    • Limit: 30 requests per window
    • Unique key: member ID or IP address
  • Key Generation:
    • Authenticated requests: Use member ID
    • Unauthenticated requests: Use IP address
    • Fallback: Use socket remote address

Rate Limit Bypass

  • Dedicated bypass middleware:
    • Separate verification logic
    • Consistent error handling
    • Comprehensive logging
  • Bypass mechanism:
    • Requires SKIP_RATE_LIMITER_KEY environment variable
    • Request must include x-skip-rate-limit header
    • Header value must match environment variable
    • 500 error if environment variable not set
    • 401 error for invalid/missing bypass key
  • Security measures:
    • All bypass attempts are logged
    • Debug logging for successful bypasses
    • Error logging for failed attempts
    • Request context included in logs

Error Handling

  • Centralized error handling:
    • Consistent error response format
    • Security-aware error messages
    • Detailed internal logging
    • Sanitized client responses
  • Security-related errors:
    • Authentication failures (401)
    • Authorization failures (403)
    • Rate limit exceeded (429)
    • Validation failures (400)
    • Server errors (500)
  • Error logging:
    • Request context (path, method, IP)
    • Error type and message
    • Stack traces (internal only)
    • User/member context when available

Development Administration

Special routes for development environments with additional security:

  • Security measures:
    • Routes not published in production
    • Requires x-dev-admin-key header
    • Separate authentication mechanism
    • Enhanced logging of all operations
  • Available operations:
    • Database management
    • System diagnostics
    • Test data operations

Environment Variables

Critical security-related environment variables:

  • JWT_SECRET
    • Required for JWT signing/verification
    • Must be strong and unique
    • Different value per environment
  • CLIENT_API_KEY
    • Required for keyhole endpoints
    • Used for client authentication
    • Must be securely distributed
  • SKIP_RATE_LIMITER_KEY
    • Optional rate limit bypass key
    • Should be used carefully
    • All usage is logged
  • DEV_ADMIN_KEY
    • Required for dev admin routes
    • Not used in production
    • All usage is logged
